One brief. A visible path to “done”.

BriefCheck turns client text into a source-backed acceptance checklist. This is a reference route through the actual code, not a claim that a learner completed a guided tour.

1. The entry point

app.js, search function generate. The button sends the brief and language to the rule engine, then renders the returned report. It warns before replacing handwritten edits.

2. Evidence and suggestions

core.js, search function analyze. Matching clauses remain the source evidence. Missing fields stay null. Suggested criteria are generated separately and start unconfirmed.

3. The agreement document

app.js, search function render, function persist and function download. User edits change report values, one browser draft stores them, and downloads keep their confirmation state. core.js · toMarkdown writes the readable document.

To change this, start here

  • Detected deliverable types or criteria: core.js · rules.
  • What counts as a concrete budget or date: core.js · fields.
  • Interface wording and samples: app.js · copy / samples.
  • Spacing, colors and mobile layout: styles.css.

A practice to reuse

An observed result treated payment “after acceptance” as acceptance criteria. A regression in tests/core.test.cjs first failed on that exact brief, then passed after the matching rule was corrected. Test an observable distinction with realistic input before trusting a fluent-looking result.
